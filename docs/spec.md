# 개인 AI 스케줄러 — 기능명세서와 사람·AI 역할 분담
작성일: 2026-10-26 | 버전: MVP v1.1 — Tool Calling·MCP 단계 및 역할 분담 반영 | 목표 배포: 2026-10-30(금)
사용자 확정: 개인용 일정 관리 웹, 자연어 일정 조회·빈 시간 확인·선택·등록, 직접 사용할 수 있는 서비스와 AI 활용 역량을 보여주는 포트폴리오. 1차는 웹의 Tool Calling을 완성하고 MCP는 후속으로 연결한다.
작성자 제안: 아래 로그인 방식·기술 조합·활동 시간·조회 한도·기본 UI 등 세부 정책. 사용자에게 이미 확정받은 사항으로 취급하지 않는다.
범위: 이 문서는 구현 기준과 역할 분담이다. 제품 코드와 배포는 아직 만들지 않았다. 이전 AI 업무 보드 명세 대신 이번 프로젝트의 기준으로 사용한다.

## 1. 무엇을 만드는가
등록된 개인 일정을 기준으로 가능한 시간을 찾아 대화로 선택하고 일정을 저장하는 웹이다.
대표 흐름:
- 사용자: “11월 2일 오후에 한 시간 수업 가능한 시간 찾아줘.”
- 시스템: 실제 일정과 활동 시간을 조회·계산해 최대 12개의 구체적인 후보를 준비하고 화면에 3개씩 표시한다.
- 사용자: “그럼 두 번째 시간에 수업 넣어줘.”
- 시스템: 앞서 제시한 후보의 실제 날짜·시간을 담은 등록 확인 카드를 표시한다.
- 사용자: 확인 버튼 클릭.
- 시스템: 현재 충돌 여부를 다시 검사하고 DB에 저장한 다음 달력·목록을 갱신한다.
AI가 도구를 선택하고 요청을 해석한다. 시간 계산·소유권·충돌 검사·저장 성공 여부는 서버와 DB가 결정한다.
등록된 데이터에 근거해 조회와 실제 저장을 연결한다. 화면에는 판단 범위를 ‘이 웹에 등록된 일정 기준’으로 표시한다.

### 1.1 개발 AI·서비스 AI·MCP 구분
| 구분 | 역할 | 이번 결과물 |
| --- | --- | --- |
| 개발용 AI | Codex·Claude Code 등으로 설계 초안·코드·테스트·리뷰를 진행 | 위임 작업·실제 검증·직접 바꾼 판단 기록 |
| 서비스 안의 AI | 사용자 요청을 해석하고 필요한 일정 도구를 선택 | Tool Calling과 짧은 대화로 실제 일정 조회·등록 |
| 서버·DB 코드 | 시간 계산·권한·중복·충돌 검사·저장 | 모델의 추정에 맡기지 않는 실행 규칙 |
| MCP 서버 | 같은 일정 기능을 외부 AI 클라이언트에 표준 도구로 제공 | 웹 MVP 이후 읽기 전용 연결부터 확장 |
Tool Calling을 위해 MCP 서버가 반드시 필요한 것은 아니다. 이번에는 일정 서비스에 도구 어댑터를 붙이고, 후속 MCP 어댑터도 같은 서비스를 호출하게 한다. MCP를 사용해 개발한 것과 제품의 MCP 서버를 만든 것은 포트폴리오에서 구분한다.

## 2. 이번 버전의 범위
### 2.1 필수
| 영역 | 이번에 구현 |
| --- | --- |
| 사용자 | 개인 계정의 일정 저장·복원·분리 |
| 기본 관리 | 일정 직접 등록·조회·수정·삭제 |
| 화면 | 주간 달력, 선택일 목록, AI 패널 |
| 활동 시간 | 사용자가 설정한 하루 활동 시간 범위 |
| AI 조회 | 날짜·기간별 일정 조회 |
| AI 빈 시간 | 원하는 날짜·시간대·소요 시간에 맞는 후보 계산 |
| AI 등록 | 직접 지정하거나 후보를 선택해 제안 생성 → 사용자 확인 → 실제 등록 |
| 대화 맥락 | 같은 대화에서 “그날”, “두 번째 시간”, 명확한 보충 답변 연결 |
| 검증 | 모호함·충돌·중복 실행·오류 처리, 핵심 테스트와 AI 평가 |
| 배포 | 실행 가능한 URL, README, 짧은 시연과 실제 AI 협업 기록 |

### 2.2 후속
MCP 서버 연결, AI 대화로 일정 수정·취소, 반복 일정, 종일·자정 넘김 일정, 팀·수강생 예약, 알림, Google/Apple/Notion 캘린더 연동, 여러 시간대, 이동·준비 시간 자동 반영, 노트·RAG.
이번 서비스는 개인 일정 도구다. 여러 사람이 같은 수업을 예약하거나 참가자의 시간을 조율하는 서비스는 범위 밖이다.
중복 일정은 허용하지 않는다. 이동 시간·휴식·외부 캘린더 일정까지 고려한 ‘실제로 반드시 가능한 시간’을 보증하지 않고, 화면에서 ‘등록된 일정 기준’이라고 표시한다.

### 2.3 구현 접근의 선택
| 방식 | 장점 | 제약 | 이 문서의 선택 |
| --- | --- | --- | --- |
| 브라우저 저장만 사용 | 빠른 시연 | 기기 간 복원·서버 권한 검증에 제약 | 화면 초안만 활용 |
| 자체 일정 DB + AI | 실제 개인 사용·충돌 검증 가능 | 인증·시간 처리가 필요 | 작성자 권장안 |
| 외부 캘린더 연동부터 시작 | 기존 일정 활용 | OAuth·동기화·외부 장애까지 다룸 | 후속 |
일주일보다 짧은 일정이므로 자체 일정 DB에 집중한다. 나중에 외부 캘린더를 연결할 수 있도록 일정 서비스와 AI 도구 호출부만 분리한다. 범용 통합 프레임워크를 먼저 만들지 않는다.

## 3. 제안 기술과 계정
| 영역 | 제안 |
| --- | --- |
| 웹 | Next.js App Router, TypeScript, Tailwind CSS |
| UI | 주간 일정 UI와 필요한 폼·다이얼로그. 달력 라이브러리 선택은 구현 AI가 크기·일정에 맞춰 제안 |
| 인증 | Supabase Auth 카카오 로그인(확정). 별도 JWT 재발급 구현은 하지 않음 |
| 저장 | Supabase PostgreSQL |
| 서버 | Next.js Route Handlers, 공통 일정 서비스 |
| 클라이언트 데이터 | TanStack Query |
| 검증 | Zod |
| AI | Groq Local Tool Calling, 초기 모델 후보 openai/gpt-oss-20b |
| 테스트 | Vitest, 핵심 UI에 React Testing Library, 대표 흐름 Playwright |
| 협업·배포 | GitHub PR·Actions, Vercel |
배포 가능한 최신 호환 버전과 Node 버전은 시작할 때 공식 문서·설치 결과로 정한다. 모델 이름은 환경변수로 관리한다.
카카오 로그인·로그아웃·세션 복원을 구현한다. 계정 설정 확장은 후속으로 둔다. 실제 카카오 OAuth 연결과 신규 계정 로그인은 배포 전에 확인한다.
공유 계정에 방문자가 개인 일정을 저장하는 구조는 쓰지 않는다. 샘플 일정은 로그인한 본인 계정에 선택적으로 추가하며 고정 키로 중복 생성을 방지한다.
포트폴리오 첫 화면에는 실제 시연 영상과 예시 요청을 제공해 로그인 전에도 기능을 이해할 수 있게 한다.

## 4. 화면과 사용 경험
| 경로·영역 | 내용 |
| --- | --- |
| / | 사용 목적·대표 시연·시작 버튼 |
| /auth | 카카오 로그인과 연결 실패 안내 |
| /schedule | 주간 달력, 선택일 일정 목록, 직접 등록 버튼, AI 패널 |
| 설정 다이얼로그 | 하루 활동 시작·종료 시간 |
데스크톱은 달력과 AI 패널을 함께 표시한다. 모바일은 선택일 목록이 기본이고 AI 패널을 열고 닫을 수 있다. 주간 이동·오늘로 이동을 제공한다.
AI 패널 구성: 요청 입력, 처리 상태, 결과 카드, 후보 버튼, 등록 확인 카드.
도구 호출 기록은 AI가 사용한 검색 조건과 결과를 개발·QA에서 확인하는 진단 정보다. 일반 사용자 화면에는 표시하지 않으며, 필요할 때 개발 환경에서만 확인한다. 일정 제목·메모·검색어 원문, 모델 내부 사고 과정, 개인정보·인증값은 기록에 노출하지 않는다.
로딩·빈 일정·조회 실패·0개의 빈 시간·저장 실패를 각각 구분한다. AI 처리 중에도 달력 탐색은 가능하다.
AI 처리·등록 버튼은 중복 제출을 막되, 서버 중복 방지도 함께 구현한다. 실패하면 입력과 확인 카드를 유지한다.
날짜와 시간을 클릭 가능한 카드에 명시한다. 숫자 순서만 표시하지 않고 ‘2026-11-02(월) 15:00~16:00’처럼 보이게 한다.
폼 label·필드 오류·키보드 이동·다이얼로그 포커스 복귀를 지원한다.

### 5.2 상대 날짜와 부족한 정보
서버가 요청 수신 시 기준 시각·날짜·요일·시간대를 계산해 AI에 제공한다. 대화 전체가 아니라 각 새 요청의 서버 시각을 기준으로 한다.
- ‘오늘’, ‘내일’, ‘다음 주 월요일’을 구체적인 날짜로 해석하고 화면에 표시한다.
- 주는 월요일~일요일이다.
- 연도 없는 날짜는 올해 날짜가 아직 지나지 않았으면 올해로 해석한다. 이미 지난 날짜라면 다음 해로 조용히 바꾸지 않고 연도를 확인한다.
- ‘오후’는 12:00 이후 활동 종료까지, ‘오전’은 활동 시작부터 12:00 전까지로 정의한다. ‘저녁’ 등 별도 정의 없는 표현은 구체 시간을 묻는다.
- ‘두 시’처럼 오전·오후를 구분할 근거가 없으면 묻는다. 모델이 임의로 오후를 선택하지 않는다.
- 날짜만 물으면 그날 일정·빈 구간을 보여줄 수 있다. 예약 가능한 고정 길이 후보를 만들거나 등록하려면 소요 시간 또는 종료 시각을 확인한다.
- 일정 제목이 없으면 등록 전에 물어본다.
- ‘가능하면 등록해줘’도 첫 버전에서는 정확한 일정 확인 카드를 표시하고 버튼 확인 후 저장한다.
정확한 숫자 날짜·시간의 유효성은 서버가 검증한다. 자연어 해석의 의미가 맞는지는 확인 카드와 평가 사례로 확인한다.

### 5.3 충돌과 빈 시간 계산
모든 일정은 [시작, 종료) 구간이다. 14:00~15:00과 15:00~16:00은 겹치지 않는다.
충돌 조건: 기존 시작 < 새 종료이고 기존 종료 > 새 시작.
빈 시간 계산: 요청 구간과 활동 시간의 교집합 → 현재 이후 시간으로 제한 → 기존 일정 구간을 빼기 → 필요한 길이의 후보 생성.
가장 이른 15분 경계부터 소요 시간만큼 배치하고, 다음 후보는 직전 후보 종료 이후부터 만들어 추천 후보끼리도 겹치지 않게 한다. 검색당 최대 12개와 hasMore를 반환한다. UI는 처음 세 개를 표시하고 이미 받은 후보를 세 개씩 더 펼친다.
소요 시간이 없으면 고정 후보 대신 연속된 빈 구간을 반환한다. 등록 단계에서 필요한 길이를 다시 확인한다.
결과가 없으면 ‘요청한 조건에 맞는 시간이 없음’을 안내한다. 조회 실패를 ‘일정이 없어서 가능’으로 바꾸지 않는다.
조회 결과가 100건을 넘으면 전체로 계산한 척하지 않고 범위를 줄이도록 한다.
충돌 검사는 AI 답변뿐 아니라 수동 등록·수정과 실제 저장 경로에도 동일하게 적용한다.

| F06 | AI 일정 조회 | ‘11월 2일 일정 알려줘’에 실제 조회 결과 표시. 조회 도구 실패 시 오류 안내 |
| F07 | AI 가능 여부 | 구체적인 시간·길이를 실제 일정과 비교. 가능/충돌 일정 표시 |
| F08 | AI 빈 시간 추천 | ‘다음 주 월요일 오후 한 시간’에 서버 계산 후보 최대 12개를 준비하고 화면에는 3개씩 표시 |
| F09 | 짧은 대화 연결 | 같은 대화의 후보·선택·조건을 이어받아 ‘두 번째 시간’, ‘그날’, ‘한 시간으로’를 해석 |
| F10 | 정보 확인 | 제목·날짜·시간·길이의 필요한 값이 없거나 모호하면 되묻고 아직 등록하지 않음 |
| F11 | AI 등록 제안 | 직접 지정 또는 유효 후보 선택으로 확인 카드 생성. 날짜·요일·시작·종료·제목 표시 |
| F12 | 확정·저장 | 사용자 확인 후 소유권·정확한 시간·현재 충돌을 재검사하고 1회 저장 |
| F13 | 제안 취소·만료 | 취소는 제안만 취소하며 기존 일정에는 영향 없음. 만료 후 새 확인 카드 필요 |
| F14 | 실패·재시도 | AI·DB 실패·한도를 구분. 이미 저장된 요청 재시도는 중복 생성하지 않음 |
| F15 | 실행 기록 | 실제 호출 도구·결과·지연 시간 기록. 등록 결과는 DB 성공에서 생성 |
| F16 | 샘플·평가 | 고정된 일정 샘플로 대표 시나리오와 실패를 재현. 실사용 일정과 샘플 구분 |
수동 수정·삭제는 잘못 등록한 일정을 바로 고칠 수 있게 하기 위한 작성자 제안이다. AI 대화 수정·취소는 이번 범위에 포함하지 않는다.

## 7. AI 도구·대화·등록 계약
### 7.1 도구
| 도구 | 모델이 제공할 입력 | 서버의 동작 |
| --- | --- | --- |
| listEvents | 날짜 범위·선택적 제목 검색 | 본인 일정 실제 조회, 결과·잘림 여부 반환 |
| findAvailability | 날짜 범위·시간대·선택적 소요 시간 | 확정된 알고리즘으로 빈 구간·후보 계산, 검색 ID와 후보 ID 발급 |
| prepareEvent | 제목, 직접 지정한 시작·종료 또는 검색 ID·후보 ID | 검증·사전 충돌 확인 후 저장할 제안만 생성 |
AI가 prepareEvent를 호출해도 일정은 생기지 않는다. 사용자 확인 요청을 서버가 처리할 때만 일정이 저장된다.
실제 조회·등록 기능은 일반 UI와 공통 일정 서비스로 공유한다. 도구 함수 이름을 eval로 실행하거나 모델의 SQL·코드를 실행하지 않는다.
최대 3회의 모델 호출, 5회의 순차 도구 실행, 전체 20초 예산을 초기값으로 제안한다. 한도에 닿으면 미저장 상태로 안내하고 종료한다.
모델 호출 실패 시 숨은 자동 재시도까지 이 예산에 포함한다. 루프를 무제한 반복하지 않는다.

### 7.2 짧은 대화 기억
같은 대화의 최근 메시지 최대 8개와 구조화한 상태를 서버에 보관한다. 구조화 상태는 대상 날짜·원하는 길이·제목·마지막 검색 결과·선택 후보·대기 제안이다.
새 검색이 성공하면 활성 후보 목록을 교체한다. 과거 후보와 현재 후보를 섞지 않는다.
‘두 번째’는 해당 대화의 활성 후보 순서에서만 해석한다. ‘그 시간’에 대응할 후보가 여러 개면 선택을 요청한다.
후보 선택 후 prepareEvent에는 해당 검색 ID·후보 ID를 사용한다. 서버가 보관한 실제 시각과 소유권·유효기간을 확인하며 모델이 새로 쓴 시각으로 후보를 바꾸지 않는다.
부족한 정보에 대한 답은 서버의 대기 상태와 연결한다. 예: ‘수업은 얼마나 하나요?’ → ‘한 시간’은 직전 등록 초안의 길이를 채운다.
대기 정보 확인 중 새 명령이 들어오면 새 요청을 우선하고 이전 초안은 폐기됐음을 표시한다. 상태 변경은 서버 응답 성공 시 확정한다.
후보·등록 초안·제안은 10분 유효. 일정 가능 시간 설정이 바뀌면 기존 후보와 pending 제안은 확정하지 않고 다시 검색·확인하도록 처리한다.
대화 패널 새로고침 시 대화는 초기화하고 일정은 유지한다. 장기 대화 복원·검색은 후속이다. 만료되거나 없는 문맥으로 임의 등록하지 않는다.

### 7.3 등록과 동시성
등록 제안은 서버에 소유자·제목·시작·종료·사용자 설정 버전·만료·상태를 저장한다. 확인 API는 제안 ID만 받고 저장된 내용을 사용한다.
확인과 실제 삽입·적용 완료 기록을 하나의 DB 트랜잭션으로 처리한다.
동시에 두 요청이 빈 시간을 조회한 뒤 저장해도 같은 소유자의 겹치는 일정은 DB에서 막아야 한다. PostgreSQL의 시간 범위 배제 제약을 우선 검토한다.
동일 제안·동일 생성 요청은 1회만 적용한다. 응답을 받지 못해 재시도해도 기존 처리 결과를 돌려준다. 같은 requestId로 다른 내용을 보내면 거부한다.
등록 완료 후 해당 일정을 수동 삭제했더라도 과거 확인 요청을 재전송해 다시 생성하지 않는다.
정확한 시간대를 모두 명시한 수동 등록과 AI 등록은 같은 경로를 사용한다. 일반 폼의 제출은 사용자의 확인으로 간주한다.
수정은 일정 version을 확인하며 다른 탭에서 바뀌었으면 덮어쓰지 않는다. 삭제는 이미 없으면 중복 삭제로 인해 다른 일정을 건드리지 않는다.
충돌 응답은 새 일정 미생성 상태와 겹치는 본인 일정 정보를 반환하고 다른 시간 찾기를 제안한다.

### 7.4 AI 출력·운영
응답 종류: events / availability / needs_input / pending_event / unsupported / error.
날짜·시간·후보 순서·조회 건수는 서버 데이터로 렌더링한다. AI의 자연어 문장만 보고 등록 성공을 표시하지 않는다.
사용자별 분당 3회·하루 15회, 프로젝트 전체 하루 100회의 AI 요청 한도를 초기 제안한다. DB의 원자적 카운터 등 지속 저장으로 검사한다.
입력·도구 인자·모델 구조화 출력은 서버에서 Zod로 검증한다. 미등록 도구와 잘못된 인자는 실행하지 않는다.
API 키는 서버에만 둔다. 서버의 확인되지 않은 오류·토큰·키를 대화나 실행 기록에 표시하지 않는다.
일정 제목·메모 안의 지시문은 데이터로 취급한다. 대화 기록·후보 ID·userId를 클라이언트가 임의로 조작해 권한을 바꿀 수 없게 한다.

### 7.5 후속 MCP 기능명세
MCP는 금요일 필수 범위가 아니다. 1차 배포·핵심 검증 후 아래 순서로 확장한다.
| ID | 단계·기능 | 완료 조건 |
| --- | --- | --- |
| M01 | 일정 조회 도구 | 외부 AI 클라이언트에서 인증된 본인 일정만 조회 |
| M02 | 빈 시간 검색 도구 | 웹과 같은 활동 시간·시간대·충돌 계산 결과 반환 |
| M03 | 권한·입력·오류 | 본인 아닌 데이터 접근 차단, 유효하지 않은 입력과 만료 인증 처리 |
| M04 | 통합 시연 | 연결한 외부 AI에서 ‘다음 주 월요일 오후 한 시간 찾아줘’를 실제 호출하고 결과 확인 |
초기 공개 도구는 listEvents와 findAvailability 두 개로 제한한다. 기존 공통 일정 서비스를 재사용하고 MCP 전용 충돌 계산을 중복 구현하지 않는다.
인증 사용자는 서버에서 결정한다. 외부 AI가 전달한 ownerId만 믿거나 Supabase 서버 전용 키를 외부 AI 클라이언트에 배포하지 않는다.
원격 연결은 MCP의 인증·전송 규격에 맞춰 구현한다. 웹 브라우저의 로그인 쿠키가 외부 AI 클라이언트에도 자동 전달된다고 가정하지 않는다.
이후 등록까지 확장할 때는 prepareEvent로 제안만 생성하고, 소유자가 웹에서 로그인한 뒤 확인하는 등 검증 가능한 사용자 확인 경로를 먼저 설계한다. ‘사용자가 승인했다’는 모델의 문장만으로 저장하지 않는다.
MCP 확장 완료 후에는 외부 클라이언트의 실제 도구 호출 기록과 웹·MCP 결과 일치 테스트를 남긴다. 웹 MVP만 완성한 상태에서 MCP 서버를 구현했다고 적지 않는다.

## 8. 데이터·API 기준안
정확한 SQL·폴더·인덱스·타입 이름은 구현 AI가 제안하되 아래 계약을 유지한다.
| 논리 데이터 | 보관할 내용 |
| --- | --- |
| events | id, owner_id, title, note, starts_at, ends_at, version, created_at, updated_at |
| user_settings | owner_id, day_start, day_end, timezone, version |
| conversations | id, owner_id, 최근 메시지·구조화 문맥·활성 후보, version, 만료 |
| event_proposals | id, owner_id, conversation_id, request_id, 입력 fingerprint, 일정 payload, settings_version, state, expires_at, result |
| ai_usage | 사용자·프로젝트 범위, 시간 구간, 카운터 |
events는 시작<종료, 제목·시간 단위 제약, 소유자별 시간 겹침 방지 제약을 둔다. user_settings는 사용자당 하나다.
event_proposals는 수동 생성·AI 제안·샘플 생성의 중복 방지 기록을 겸한다. 별도의 복잡한 이벤트 소싱을 만들지 않는다.
AI 요청 requestId도 대화 내 유일성을 보장하고 완료 결과를 재사용한다. 다른 입력으로 재사용하면 409. 중복 요청을 받았다고 새 LLM 호출을 시작하지 않는다.
한 대화의 동시 요청은 conversation version으로 충돌을 감지해 한 번에 하나만 진행한다. 로딩 중인 UI 차단만 믿지 않는다.
| API | 역할 |
| --- | --- |
| GET /api/events | 날짜 범위별 본인 일정 |
| POST /api/events | 일반 폼 생성, requestId 포함 |
| PATCH /api/events/:id | 본인 일정 수동 수정, version 포함 |
| DELETE /api/events/:id | 본인 일정 삭제 |
| GET·PATCH /api/settings | 활동 시간 조회·수정 |
| POST /api/chat | 새 메시지와 conversationId·version. 도구 호출·결과 또는 확인 카드 반환 |
| POST /api/proposals/:id/confirm | 저장된 등록 제안 확정 |
| POST /api/proposals/:id/cancel | 제안 취소 |
| POST /api/demo/seed | 고정 샘플의 본인 계정 1회 생성 |
공통 오류: 400 잘못된 입력, 401 인증 필요, 404 본인 범위에서 대상 없음, 409 충돌·버전·requestId 문제, 410 제안 만료, 429 사용 한도, 502 모델 오류, 504 시간 초과.
서버는 검증된 Supabase 인증에서 owner_id를 결정한다. getSession에서 읽은 사용자나 클라이언트 userId만으로 권한을 결정하지 않는다.
RLS를 활성화하고 자기 데이터만 읽게 한다. 변경은 검증된 서버 경로로 모으고 브라우저의 직접 테이블 쓰기로 제안·중복 방지 정책을 우회하지 않게 한다.
서버 전용 권한·RPC 중 방식은 구현자가 선택하되 모든 경로에서 소유권과 공통 규칙을 강제한다. 강한 권한은 RLS를 우회할 수 있음을 고려한다.
개인별 응답은 공유 정적 캐시·공유 CDN에 저장하지 않는다. 쿠키 인증 변경 요청의 같은 출처도 확인한다.
이 데이터 구조는 구현 편의를 위한 기준안이며 작업을 쪼개면서 단순화할 수 있다. 시간·소유권·중복·문맥 계약은 유지한다.

| T12 | 자정·월말·연말·주 경계 상대 날짜 | Asia/Seoul 정책과 일치 |
| T13 | 조회 실패·100건 초과·모델 오류·미등록 도구 | ‘비어 있음’이나 성공으로 처리하지 않음 |
| T14 | 동시 사용량 제한·대화 version 충돌 | 한도와 문맥 일관성 유지 |
시간 계산은 고정 시각으로 검증한다. 동시 저장·소유권 제약은 테스트 DB에서 확인한다. mock만으로 DB 보장이 증명됐다고 보고하지 않는다.

### 9.2 실제 AI 평가
15개 질문을 고정한다: 조회 3, 빈 시간 4, 등록·대화 연결 4, 모호함·미지원·실패 4.
질문별 기준 날짜·샘플 일정·예상 도구·필수 인자·변경 여부를 기록한다. 날짜·기록 순서가 달라 평가가 흔들리지 않게 한다.
문장 일치율만 보지 말고 실제 도구 인자·서버 결과·DB 등록 여부를 확인한다. 실제 모델 호출 결과와 모델을 대체한 코드 테스트 결과는 구분한다.
프롬프트·모델 버전, 실패 사례, 바꾼 이유와 재평가 결과를 남긴다. 실제로 측정하지 않은 성공률·시간 절감·비용 절감을 성과로 적지 않는다.

### 9.3 브라우저·CI
대표 E2E: 로그인 → 샘플 일정 → 빈 시간 요청 → 두 번째 후보 선택 → 확인 → 달력 반영.
CI에서는 모델 응답을 고정하고 실제 AI 평가는 별도로 수행한다. 두 사용자 격리, 모바일·키보드·새로고침·두 탭 충돌도 확인한다.
package.json에 typecheck, lint, test:run, build 명령을 실제로 정의하고 GitHub Actions에서 실행한다. E2E 스크립트도 정의하고 배포 전에 실행 결과를 남긴다.
개발·CI용 mock 모드는 서버 설정으로만 활성화하며 운영에서 임의 요청으로 켤 수 없게 한다.

### 10.3 작업 전달·완료 보고 방식
손 대표님은 사용자 문제·범위·기대 결과를 전달하고, AI는 구현 방법·변경·검증 결과를 제시한다. 모든 함수 작성법을 손 대표님이 미리 지정할 필요는 없다.
작업 하나의 요청에는 목표, 이번 변경 범위, 반드시 유지할 규칙, 완료 조건을 담는다.
AI 완료 보고는 ‘변경 요약 / 실제 실행한 검사와 결과 / 손 대표님이 직접 확인할 시나리오 / 남은 제한’으로 작성한다.
AI가 완료했다고 말한 사실과 실제 동작·검증 결과를 구분한다. 문제가 있으면 해당 기능을 수정하고 확인한 뒤 다음 작업으로 이동한다.

### 직접 이해할 코드 5곳
1. 요청을 도구 호출로 해석하고 인자를 검증하는 곳.
2. 대화의 날짜·길이·후보 선택 상태를 저장하는 곳.
3. 빈 시간과 충돌을 계산하는 곳.
4. 확인 후 실제 등록하며 중복·동시 실행을 막는 곳.
5. 저장 성공 후 달력·목록을 갱신하는 곳.
이 코드도 AI에게 작성하게 할 수 있다. 다만 선택 이유와 테스트를 설명할 수 있게 읽고 확인한다.
반복 JSX·폼·타입 초안·마이그레이션·CI·테스트 초안은 적극 위임한다. 코드 전부를 손으로 작성해야 AI 활용 역량이 증명되는 것은 아니다.

### 손 대표님이 준비할 것
- 로컬 프로젝트 폴더와 GitHub 저장소, 사용할 코딩 도구 하나.
- Supabase·Groq·Vercel 계정 및 프로젝트.
- 실제 환경변수는 로컬 .env.local·배포 설정에 직접 입력. 비밀값은 문서·채팅·커밋에 넣지 않는다.
- 본인 활동 시간과 시연할 일정 예시, 실제 사용할 요청 3~5개. 나머지 평가 질문 초안은 AI가 확장하고 손 대표님이 기대 결과를 확인한다.
AI는 실제 비밀값 대신 필요한 환경변수 이름을 담은 .env.example을 작성한다. Supabase 사이트 URL·카카오 OAuth 리다이렉트와 Groq 가용 모델을 배포에서 확인한다.

## 12. AI에게 작업을 맡기는 방식
저장소에 이 파일을 docs/spec.md로 넣는다. AGENTS.md 또는 코딩 도구의 지침에는 범위·구조·코드 스타일·검증 명령을 짧게 정리한다.
개발 단위: setup → calendar-core → availability → ai-query → ai-booking → release. 후속 단계는 mcp-readonly이다. 아주 작은 수정마다 별도 PR을 만들 필요는 없다.
기능 하나마다 요구사항·완료 조건 → AI 구현 → 직접 조작·diff 확인 → 테스트·리뷰 → 다음 기능 순서로 진행한다.
처음에는 구현 세션 하나로 충분하다. 리뷰는 별도 대화에 spec과 diff를 제공한다. 병렬 구현을 할 때는 독립 브랜치·worktree로 격리한다.
AI가 테스트를 약하게 바꾸거나 타입 오류를 숨겨 통과시키지 않도록 한다. 테스트 실패·환경 미설정·실행 못 한 항목을 보고서에서 구분한다.
코드 스타일: 기존 코드 우선, 불필요한 빈 줄과 trailing comma 금지, 컴포넌트·함수의 구조분해 props 매개변수는 가능한 한 줄.
포트폴리오에 남길 것: 배포·시연, AI 위임 작업, 직접 수정·거절한 설계 사례 2~3개, 실제 테스트·평가 결과, 남은 제한.
실제 사용 중 잘못 해석한 요청과 개선 사례도 남긴다. 구현한 범위에 한해 Tool Calling, 대화 맥락, 확인 후 실행, 후속 MCP를 각각 설명한다.
개발용 MCP(예: 브라우저 검증 도구 연결)를 사용했다면 별도로 기록한다. 일반 Playwright 테스트 실행만 했다면 MCP를 활용했다고 적지 않는다.

### 첫 작업 요청
> docs/spec.md를 읽고 개인 AI 스케줄러를 개발하려고 한다. 목표는 10월 30일 배포이며 핵심은 실제 일정 조회 → 빈 시간 계산 → 대화로 후보 선택 → 확인 후 등록이다.
>
> 현재 폴더와 실행 환경을 확인하고, 문서에서 미정인 기술 선택과 필요한 환경변수 이름을 정리해줘. 내 비밀값을 요청하거나 출력하지 마.
>
> 먼저 전체 구현 순서와 오늘 작업의 변경 파일·완료 조건을 제안해줘. 내가 확인하면 오늘 범위부터 구현해줘. 프로젝트 전체를 한 번에 구현하지 마.
>
> 첫 구현은 실행 환경·저장소 지침·CI·가짜 일정으로 동작하는 화면 초안이다. 이후 인증·DB·시간 계산, AI 조회, 대화 등록 순서로 진행한다. MCP 서버는 이 MVP가 동작하고 검증된 다음의 별도 단계로 두고, 같은 일정 서비스를 재사용할 수 있게 경계를 나눠줘.
>
> 구현 후 실제 실행한 검증 결과, 내가 브라우저에서 확인할 항목, 남은 작업을 알려줘. 불필요한 빈 줄과 trailing comma를 피하고 props 구조분해 매개변수는 가능한 한 줄로 작성해줘.
