# Auth and DB Foundation Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Add Supabase email authentication, a protected real-schedule shell, and owner-scoped database foundations without exposing actual credentials.

**Architecture:** Supabase SSR browser/server clients share cookie sessions. Next.js Proxy refreshes sessions while protected pages independently verify claims. A versioned SQL migration creates owner-scoped tables with read-only RLS; later PRs add validated mutation paths.

**Tech Stack:** Next.js 16 App Router, TypeScript, @supabase/ssr, @supabase/supabase-js, PostgreSQL

**Spec:** `docs/superpowers/specs/2026-10-27-auth-db-design.md`

## Global Constraints
- Do not read, print, commit or request real environment values.
- Keep the anonymous sample demo labeled as sample; /schedule must not display sample events as DB events.
- No secret or service role key in browser code.
- Ownership comes from verified auth, never client-supplied owner_id.
- No direct table writes from browser in this PR.
- Use Node 24.22.1 and pnpm; preserve current code style.

## Review Focus
- Forged or expired cookies must not expose /schedule.
- Logging out must prevent subsequent /schedule access.
- An email confirmation URL must not redirect to an arbitrary external origin.
- RLS must deny anonymous reads and cross-account rows.
- Proxy session refresh must preserve refreshed cookies.
