# 개인 계정과 일정 DB 보안 기반 디자인

## 목적
손 대표님이 Supabase Auth 이메일·비밀번호로 로그인하고, 이후 실제 일정을 본인 계정에만 저장할 수 있는 기반을 만든다. 이 단계의 화면은 실제 DB 일정이 아직 연결되지 않았음을 분명히 표시한다.

## 접근 방식
- **선택: Supabase SSR 세션과 PostgreSQL RLS.** Next.js 서버에서 검증된 사용자 클레임을 확인하고, DB도 소유자별 읽기 권한을 강제한다. UI와 DB에 각각 방어선을 둔다.
- 대안: 브라우저 로컬 저장은 계정 간 복원과 DB 권한 검증이 불가능하다.
- 대안: 자체 JWT 인증은 이번 일정에 불필요한 인증·세션 관리 부담을 더한다.

## 화면과 인증 흐름
- `/`는 현재 샘플 체험을 유지하고 `/schedule`로 가는 시작 링크를 제공한다.
- `/auth`는 이메일 가입·로그인 전환, 필드 오류와 메일 확인 안내를 제공한다.
- 메일 확인 링크는 `/auth/confirm`에서 서버가 토큰을 검증해 세션을 만든다. 성공 시 `/schedule`, 실패 시 `/auth`에서 재시도를 안내한다.
- `/schedule`은 로그인한 사용자만 볼 수 있으며 이번 단계에는 실제 일정 없음 상태와 로그아웃을 표시한다. 샘플 데이터를 실제 일정으로 보이지 않는다.
- Next.js 16 Proxy는 Supabase 세션을 갱신한다. 페이지·API 권한은 Proxy만 믿지 않고 서버에서 `getClaims()`로 확인한다.
- 로그아웃 후 `/schedule` 접근은 로그인 화면으로 돌아간다. 개인 응답은 공유 캐시를 사용하지 않는다.

## 데이터와 권한
- 첫 마이그레이션에서 `events`와 `user_settings`를 만들고 `owner_id`를 `auth.users`에 연결한다.
- `events`는 제목, 선택적 메모, 시작·종료, 버전, 생성·수정 시각을 가진다. 소유자별 겹침은 PostgreSQL 범위 배제 제약으로 막는다.
- `user_settings`는 사용자당 하나이며 기본 활동 시간 09:00~21:00, 시간대 Asia/Seoul, 버전을 가진다.
- 두 테이블 모두 RLS를 켜고 로그인한 사용자의 본인 행 읽기만 허용한다. 브라우저의 직접 쓰기는 닫아 둔다. 실제 쓰기 경로와 제약 검증은 다음 일정 관리 PR에서 연다.
- 서버는 클라이언트가 보낸 `owner_id`를 신뢰하지 않는다.

## 범위와 검증
- `.env.example`에는 공개 프로젝트 URL·publishable key의 변수 이름만 적는다. 실제 값은 읽거나 커밋하지 않는다.
- 기존 샘플 달력, 월간 보기, 샘플 AI 패널은 유지한다. 실제 일정 CRUD·AI 연결은 이번 PR 범위 밖이다.
- 코드 검사: 테스트·타입 검사·린트·빌드. 실제 완료 판정에는 두 계정 격리, 로그아웃 차단, 메일 확인, DB RLS 테스트가 필요하다.
- 로컬 DB나 실제 Supabase 접근이 없는 검사는 미실행으로 표시하고 Draft PR에 남긴다.
