# 실제 일정 조회·직접 관리 설계

## 목적
로그인 사용자가 본인 실제 일정을 조회하고 등록·수정·삭제한다. 샘플 일정 화면과 실제 계정 일정은 분리한다.

## 범위
- `/schedule`에서 주간·월간 달력과 선택일 일정을 DB에서 읽는다.
- 기간 이동, 오늘 이동, 직접 일정 등록·수정·삭제를 제공한다.
- 제목·시간·길이, 충돌, 소유권, 수정 버전을 서버와 DB에서 검증한다.
- 성공 후 목록을 갱신하고 실패하면 입력과 오류 안내를 보존한다.
- AI, 활동 시간 설정, 빈 시간 검색, AI 후보 등록은 별도 이슈에 둔다.

## 접근 방식
- **선택: Server Actions + 세션 인증 DB 함수.** Server Action은 세션을 확인하고 사용자 ID를 클레임에서 얻는다. 일정 변경은 로그인 JWT가 전달되는 제한된 PostgreSQL 함수로 실행하며 함수가 `auth.uid()`를 소유자로 사용하고 DB 제약을 최종 적용한다. 브라우저의 테이블 직접 쓰기 권한과 service role 키는 사용하지 않는다.
- 대안: Server Action에서 service role로 테이블을 직접 변경하면 RLS를 우회하는 비밀키와 수동 소유권 검사가 필요하다.
- 대안: 브라우저에 인증된 쓰기 권한을 주면 RLS로 소유권은 제한할 수 있지만, 테이블 직접 쓰기 차단 결정을 바꿔야 한다.

## 동작 기준
- 읽기는 현재 세션의 Supabase SSR 클라이언트와 RLS를 사용한다.
- 생성·수정·삭제 Server Action은 매 호출마다 사용자 클레임과 입력을 검증한다.
- DB 함수는 모든 변경을 `auth.uid()`의 행으로 제한하고 길이·시간·겹침·버전 조건을 검사한다. 원본 테이블 INSERT/UPDATE/DELETE 권한은 계속 거부한다.
- 기존 `events` 테이블 제약을 재사용한다. 오래된 버전 수정은 충돌로 반환하고 삭제도 기대 버전을 확인한다.
- 실제 달력은 기존 색상·간격과 주간/월간 전환을 따르되 샘플 대화 패널을 실제 기능처럼 표시하지 않는다.

## 완료 조건
- 본인 일정만 조회·등록·수정·삭제되고 새로고침 후 유지된다.
- 잘못된 값, 부분 겹침·동일 시간, 오래된 편집 버전이 거부된다. 연속 일정은 허용된다.
- 삭제 확인, 저장·조회 오류, 빈 일정 상태를 확인한다.
- 실제 서비스 테스트와 CI 결과를 로컬 검사와 분리해 기록한다.

## 구현자 판단
- 기존 React/CSS 관례를 따르며 필요한 폼과 액션만 추가한다.
- 일정 기간은 주간/월간 그리드 범위로 읽고 모든 기간 이동에서 선택 날짜를 일관되게 갱신한다.

## UI 개선 추가 결정
- 선택된 날짜의 테두리는 달력 하단 모서리에서 잘리지 않도록 그리드의 바깥 모서리 형태를 따른다.
- 날짜는 기존 주/월 달력과 같은 시각 언어의 팝오버 달력에서 선택한다.
- 시작·종료 시각은 브라우저별 `datetime-local` UI 대신 15분 단위 시간 선택으로 고른다. 종료 시각 선택지는 시작 후 15~240분, 같은 날짜 범위로 제한한다.
- 날짜·시간 선택은 기존 Server Action과 서버 검증을 그대로 사용하며, 모바일에서 터치할 수 있는 크기와 키보드 접근성을 유지한다.
