# 이슈 10 검증 설계

## 목표

배포 전에 로그인 사용자의 일정 흐름, 계정 격리, 충돌·중복 저장, 모바일·키보드 사용성을 재현 가능하게 확인하고, 고정 테스트와 실제 AI 평가 결과를 분리한다.

## 현재 기반

- 기존 자동화는 Node 테스트와 GitHub Actions의 타입 검사·린트·테스트·빌드다.
- 브라우저 E2E, 실제 DB 동시성 테스트, 15개 AI 평가 러너는 아직 없다.
- 저장소에는 Supabase CLI 프로젝트 설정이 없으므로 원격 DB를 임의로 변경하거나 연결하지 않는다.
- 실제 Kakao 로그인과 모델 평가에는 전용 테스트 계정, 인증 세션 파일, AI API 환경변수가 필요하다.

## 선택

1. Playwright E2E는 테스트 사용자 세션 상태 파일을 외부 경로에서 받아, 운영 개인 계정 대신 전용 테스트 계정으로 실행한다. 저장 상태 파일은 저장소에 두지 않는다.
2. 브라우저 흐름에서는 AI 응답을 통제해 후보 선택·등록 확인 UI를 반복 가능하게 검증하고, 별도의 실제 AI 평가 명령은 인증된 테스트 사용자의 `/api/chat`를 호출한다.
3. 실제 AI 평가는 질문·도구 호출·도구 결과·일정 상태만 요약해 Markdown/JSON 보고서로 남긴다. 입력 원문, 일정 제목·메모, 인증값, 모델 내부 사고는 기록하지 않는다.
4. 두 계정 격리와 동시성 테스트는 전용 테스트 계정과 설정된 테스트 DB에서만 실행한다. Supabase 로컬 구성이 없는 현재는 원격 DB 테스트를 자동으로 실행하지 않는다.

## 범위 밖

인증·일정 API·DB 정책을 바꾸지 않는다. 프로덕션 DB에 샘플 데이터를 추가하지 않는다. 실제 AI 결과를 고정 테스트 통과로 간주하지 않는다.

## 미실행 조건

전용 테스트 계정·세션 파일·테스트 DB 설정이 없으면 해당 실서비스 검증은 안전하게 건너뛰고, 필요한 환경변수 이름만 보고한다. 실제 AI 평가 실행은 모델 사용량과 테스트 DB를 소비하므로 고정 테스트와 명령을 분리한다.
